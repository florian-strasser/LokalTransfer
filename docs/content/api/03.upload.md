# Uploading files

There are two ways to get a file into a draft. A single request is the simple
one, and all a script needs for anything of ordinary size. For large files, or
over a connection you do not trust, send the file [in pieces](#resumable-uploads)
instead: an interruption then costs seconds rather than the whole upload.

## One request

```http
POST /api/transfers/:id/files
Content-Type: multipart/form-data
```

One file per request, sent as a `file` field:

```bash
curl -X POST "$BASE/api/transfers/$ID/files" \
  -H "x-api-key: $KEY" \
  -F "file=@build.zip"
```

```json
{
  "data": {
    "id": 41,
    "filename": "build.zip",
    "mimeType": "application/zip",
    "size": 48213004
  }
}
```

The body is piped straight to disk rather than read into memory. For a service
whose job is multi-gigabyte files, that is the difference between working and
running the process out of memory on the first real transfer.

One file per request also means the client gets true per-file progress, a
failure costs only that file, and the size limit can be enforced **mid-stream**
rather than after everything has already arrived.

An upload may take as long as it needs: there is no limit on its duration, only
on silence. A connection that delivers nothing for two minutes is dropped, and
its partial file removed.

## Resumable uploads

A file sent in pieces, any of which can be sent again. This is what the web
interface uses.

**1. Announce the file.** Nothing is uploaded yet; you say what is coming and
get an upload id back.

```bash
curl -X POST "$BASE/api/transfers/$ID/uploads" \
  -H "x-api-key: $KEY" -H "Content-Type: application/json" \
  -d '{"filename": "build.zip", "size": 3221225472}'
```

```json
{
  "data": {
    "id": "0b6f7c1e-…",
    "offset": 0,
    "size": 3221225472,
    "chunkSize": 16777216,
    "complete": false
  }
}
```

`chunkSize` is the piece size the web interface uses. It is advice: the server
accepts pieces of any size, including the whole file in one.

**2. Send the pieces.** The body is the raw bytes; `Upload-Offset` says where in
the file they start.

```bash
curl -X PATCH "$BASE/api/transfers/$ID/uploads/$UPLOAD" \
  -H "x-api-key: $KEY" -H "Upload-Offset: 0" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @piece-000
```

```json
{ "data": { "id": "0b6f7c1e-…", "offset": 16777216, "size": 3221225472, "complete": false } }
```

The piece that brings `offset` up to `size` completes the upload, and its
response carries the finished file:

```json
{
  "data": {
    "offset": 3221225472,
    "size": 3221225472,
    "complete": true,
    "file": { "id": 41, "filename": "build.zip", "mimeType": "application/zip", "size": 3221225472 }
  }
}
```

**3. After an interruption, ask where to carry on.**

```bash
curl "$BASE/api/transfers/$ID/uploads/$UPLOAD" -H "x-api-key: $KEY"
```

```json
{ "data": { "id": "0b6f7c1e-…", "offset": 1811939328, "size": 3221225472, "complete": false } }
```

Whatever arrived before the connection dropped is kept — including part of a
piece — so `offset` is the exact byte to send from next, not the start of the
piece that failed.

### The rules

- **A piece is only accepted at the end of what has arrived.** Anything else
  answers `409 OFFSET_MISMATCH` with the real `offset` in the body, and writes
  nothing. Pieces therefore cannot overlap, leave a gap or arrive out of order,
  and sending the same piece twice is harmless.
- **One writer at a time.** A piece sent while another is still being written
  into the same upload answers `409 UPLOAD_BUSY`. This is normal straight after a
  dropped connection, while the server is still letting go of the dead request:
  wait a moment and try again.
- **The answer to a lost reply is kept.** If the last piece arrived but its
  response did not, asking again answers `complete: true` with the file.
- **More than was announced is refused** with `400 CHUNK_TOO_LARGE`, and none of
  that piece is kept.
- **An unfinished upload blocks sending.** The transfer answers
  `409 UPLOADS_INCOMPLETE` until every upload is finished or withdrawn:

  ```bash
  curl -X DELETE "$BASE/api/transfers/$ID/uploads/$UPLOAD" -H "x-api-key: $KEY"
  ```

  A file that is still arriving is never left out of a transfer quietly.

An upload nobody finishes goes with its draft, which is swept after
`NUXT_DRAFT_MAX_AGE_HOURS`.

## Limits

| Limit | Default | Variable |
| --- | --- | --- |
| Per file | 2048 MB | `NUXT_MAX_FILE_SIZE_MB` |
| Files per transfer | 50 | `NUXT_MAX_FILES_PER_TRANSFER` |

Exceeding the size limit aborts the stream and removes the partial file, so
nothing is left occupying disk under a row that was never written. A resumable
upload is refused when it is announced, before a byte is sent
(`413 FILE_TOO_LARGE`). Files still arriving count towards the per-transfer
limit.

## Only into a draft

A transfer accepts files only while its status is `draft`. Once sent, the file
list is what the recipient was told they are getting, so a further upload
answers `409 TRANSFER_ALREADY_SENT`.

Someone else's transfer answers `404`.

## Filenames

The name you send is stored in the database and reattached in the
`Content-Disposition` header on the way out. On disk the file gets a random
name.

That removes path traversal, reserved Windows names, unicode normalisation
collisions and case-insensitive overwrites as a class of problem, rather than
trying to sanitise them one by one.
